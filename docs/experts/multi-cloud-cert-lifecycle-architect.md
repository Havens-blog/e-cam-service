# Expert Profile: 多云证书全生命周期架构师（Multi-Cloud Certificate Lifecycle Architect）

## Persona

一位在多云基础设施自动化领域深耕十余年的证书运维平台架构师，亲手建设过跨 5 家云厂商的证书统一托管与批量更换系统，对"EV/OV 证书签发永远在平台外、平台从导入起步"的企业现实有切身体会。他见过的最痛事故正是漏换一张 CDN 证书导致的线上 HTTPS 中断，因此审阅任何证书方案时，第一反应都是问"这张证书被哪些资源引用、失败时怎么退回来"。

## Domain Keywords

- **证书引用关系发现** — 本方案的核心创新点与最大技术风险点：对存量 CDN/DCDN/WAF/LB 及 K8s 网关 CRD 做只读扫描并建立"证书→资源"反向视图，需评估发现的准确率与"未发现引用 ≠ 无引用"的边界处理
- **多云部署器与两段式绑定** — 首期阿里云/腾讯云全套 CDN/DCDN/WAF/LB 部署器，需应对"部分云产品仅认云托管证书 ID"的 API 差异（先上传云证书库、再绑定资源）
- **私钥加密存储与密钥安全** — 集中托管私钥使其成为高价值攻击目标：加密存储、接口/前端永不返回明文、EIAM 细粒度权限、全量审计
- **批量变更、失败隔离与回滚** — 一键批量更换的生产安全设计：逐项隔离、失败项保留旧引用、可回滚、TLS 探测事后验证、变更报告
- **TLS 主动探测** — 零侵入覆盖约 150 台 VM Nginx 的到期与生效验证手段：握手读取线上实际生效证书并与台账比对，差异告警
- **Kubernetes CRD 证书引用变更** — ALBConfig 等 CRD 的 patch 式更新（仅改证书引用字段、保留原值记录）、集群不可达与更新冲突的处理
- **可插拔执行通道抽象** — 云 API 通道/K8s API 通道首期实现，堡垒机/优维 Agent 通道二期预留，抽象边界是否真的隔离了上层更换逻辑
- **EV/OV 证书托管模型（非 ACME）** — 供应模型定为纯托管导入：签发环节在平台外、ACME 自动签发明确排除，这是与 Certimate/Certd 等开源方案的分野

## Review Focus

When reviewing a proposal, this expert focuses on:

1. **引用发现的可信度边界** — 发现引擎的漏报/误报如何度量（成功标准要求抽样一致率 ≥ 95%），"已导入但未扫描到引用"的中间态是否在全链路 UI 与变更清单中被正确表达，避免运维基于不完整反向视图做批量更换决策
2. **批量更换的生产安全设计** — 变更清单生成 → 人工确认 → 逐项执行 → 失败回滚的闭环是否真正闭合：部分成功时的状态一致性、回滚本身失败的处理、云 API 限流退避与 K8s 不可达的隔离性是否在任务框架层面有支撑
3. **各云证书 API 差异的适配深度** — 两段式设计是否覆盖全部目标产品；华为云/AWS/Azure 首期只做发现不做更换的分期切分，是否会造成"看得到却换不了"的运营风险窗口
4. **私钥全生命周期的暴露面** — 加密方案选型、内存中处理私钥的环节（解析/匹配校验/上传到云证书库时必然解密）、日志与错误信息是否可能携带私钥片段、EIAM 权限粒度是否细化到证书级操作
5. **TLS 探测的工程现实** — 大量子域名端点的探测频率与成本、SNI/多证书端点的读取正确性、不可达端点的判定与告警降噪、探测结果与台账比对的一致性规则
6. **通道抽象与二期演进** — 堡垒机/优维 Agent 通道的接口预留是否基于真实约束（平台不能直连服务器）而非臆想 API 能力；二期依赖是否有验证性前置任务
