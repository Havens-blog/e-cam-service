## Phase 1 — Reasoning Audit（赛前独立判断）

**Problem → Solution 追踪**：问题定义把"约 150 台 VM Nginx 上逐处更换"列为一等痛点（Problem 段与 Evidence 段各提及一次），但首期方案对 Nginx 只提供"TLS 探测到期监控"，更换与配置级引用发现全部延到二期，且二期通道本身带有 M/M 风险（"二期堡垒机自动化 API 受限，VM Nginx 更换通道受阻"）。即：**问题陈述中体量最大的手工变更面（150 台 VM）在首期交付中零更换能力**。文档在 Out of Scope 中诚实地承认了这一点，不构成硬矛盾，但削弱"方案解决了所述问题"的完整性——首期解决的是云资源 + K8s 网关那部分，而那部分按 Evidence 的描述（"每次换证全网重复此类操作十几处"，例子给的是 K8s）体量可能反而是小的。

**Evidence → 判断**：证据是具体可核实的（操作路径示例、150 台、十几处），但缺量化：无证书总数、无单轮换证耗时、无历史漏换事故记录。"换证频繁（付费证书周期短）"未给出周期或张数。

**SC → 关键点**：SC 覆盖了 In Scope 的大部分，量化口径总体可测；但"回滚成功率 100%"是绝对化承诺，而回滚本身也是一次云 API 变更，无法保证 100%。文档自带 consistency_check_result（36 对检查、1 处已修复），可信度加分。

**SC 一致性深查（聚类 + 双向可满足性）**：

- 聚类 A（托管/导入）：SC-1 ↔ InScope-1/2，可满足，无矛盾。
- 聚类 B（引用发现）：SC-2（5 云 + K8s，≥95%）↔ InScope-3（全云只读），对齐。
- 聚类 C（更换）：SC-4/SC-5（≥95%、回滚 100%）↔ InScope-7，可满足但回滚口径未定义范围（见 blindspot）。
- 聚类 D（监控告警）：SC-3/SC-6 ↔ InScope-4/5，对齐；但 InScope-4 将"webhook + 邮件渠道"列为一期交付，而 Dependency Readiness 写"通道待确认，接口预留"——交付物与依赖就绪状态存在张力（软矛盾，非硬冲突）。

**软矛盾标记（attack point，非 CONTRADICTION 级）**：
INSCOPE-TENSION: InScope-4 "webhook + 邮件渠道" ↔ Dependency "告警渠道…通道待确认" | Type: 交付承诺 vs 依赖就绪 | Evidence: 两处原文 | Resolution: 明确一期交付的渠道范围或降级为"接口预留"。

**自反性检查（方案是否重新引入它要消除的问题）**：两段式上传（先传云证书库再绑定）会在各云产生平台外的证书副本，"统一台账"对这些云上副本的生命周期（旧副本清理）无说明——轻微，不构成重新引入手工问题。

## Phase 3 — Blindspot Hunt（rubric 之外的领域专家盲区）

1. **[blindspot] 回滚语义未定义**："失败项保留旧证书引用并可一键回滚"（错误场景）+ SC-4 "失败项可回滚且回滚成功率 100%"——对执行失败项而言引用未变，回滚是空操作；真正需要回滚的是部分成功批次中的已成功项。回滚的作用对象（逐项/整批/仅成功项）与操作语义全文未定义，SC-4 的 100% 因此不可验证。
2. **[blindspot] 删除被引用证书无防护**：InScope-1 含"删除"，但边界场景与 SC 均未覆盖"删除仍被线上资源引用的证书"。此类删除会破坏"证书 → 资源"反向视图的完整性，使后续同域名匹配更换漏点——恰好是本方案要消除的"漏换"风险的另一种引入方式（方案部分重新引入它声称消除的问题，程度轻微但真实）。
3. **[blindspot] 监控-only 场景被私钥强制绑定**：导入格式为"证书 + 私钥"（InScope-1），TLS 探测目标为"托管子域名端点"（SC-6）。对只想纳管到期监控、不打算经平台更换的证书（例如三期才支持的平台），持有私钥不是必要条件——强制私钥使纳管门槛被人为抬高，且扩大了"私钥集中存储"攻击面而不产生对等收益。
4. **[blindspot] 云证书库副本的生命周期无归属**：两段式更换在各云证书库持续产生上传副本（每次换证一份），旧副本是否清理、由谁清理（平台自动/云侧自动/人工）全文未提，长期将造成云证书库垃圾堆积与"哪个 ID 才是生效的"歧义——后者直接影响引用发现按指纹/域名关联的准确性。
