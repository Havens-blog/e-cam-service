# Eval Report — SSL 证书统一托管与更换平台 Proposal（Iteration 1）

## Phase 1 — Reasoning Audit（独立判断）

**Problem → Solution**：问题（多云手工换证、无台账、易漏换）与方案（托管台账 + 引用发现 + 批量更换）主链路成立。但注意两点张力：
1. 问题段将"约 150 台 VM Nginx"列为核心痛点之一，而首期方案对 Nginx 只做 TLS 探测监控，更换仍靠手工——方案已显式声明该边界（Out of Scope + 风险表），属诚实的分期切分而非隐瞒，但对"解决问题"的完整性构成折扣。
2. "平台不能直连 VM Nginx"（约束）与"TLS 主动探测……握手即可读取线上生效证书"（方案 4）之间存在未声明的网络可达性假设（详见 D10 与盲区分析）。

**Solution → Evidence**：方案对现有能力（云账号凭证、资产同步、异步任务框架、EIAM）的复用主张均落到了 Feasibility 段的"已有 ✅"，闭环成立。

**Evidence → Success Criteria**：痛点"无法回答这张证书被哪些资源引用"直接映射到引用发现 SC（一致率 ≥95%、覆盖率 ≥99%），映射良好。

**自反性检查（方案是否重新引入其声称消除的问题）**：未发现。方案声称消除"全网手工变更"，首期在阿里云/腾讯云 + K8s 上确实闭环；华为/AWS/Azure 与 Nginx 仍手工但已显式声明。

**SC Consistency Deep-Dive**：逐对检查了 SC 集合与 In Scope 条目，未发现不可同时满足的硬矛盾。发现两处歧义（非矛盾，需作者澄清）：

- AMBIGUOUS-1: SC-5 "旧证书已删除或已过期的项不自动回滚" ↔ 台账规则"存在活跃引用……禁止删除"。平台侧删除已被"非零引用拦截"阻断，故"旧证书已删除"只能指云侧证书库删除，但文档未区分"平台删除"与"云侧删除"两种语义。Type: 语义歧义 | Evidence: "删除非零拦截：存在活跃引用或处于回滚保护期内的证书禁止删除" vs "旧证书已删除或已过期时不自动回滚" | Resolution required: 明确"旧证书已删除"指云侧证书库中的旧证书被删除。
- AMBIGUOUS-2: 告警渠道门控不对称。SC-4 到期告警有前置门控（"渠道确认完成前本项不进入验收"），但 SC-8 TLS 差异告警与"变更关联告警"同样依赖告警渠道，却无同等门控。Type: 内部一致性 | Evidence: "告警渠道确认为前置依赖，确认完成前到期告警相关成功标准不进入验收" vs "能识别线上生效证书与台账不一致并告警" | Resolution required: 明确差异告警/变更关联告警是否同样受渠道确认门控约束。

## Phase 2 — Rubric Scoring

### 1. Problem Definition: 98/110

- 清晰（38/40）：问题单义、场景具体（"这张证书被哪些资源引用"），两个读者不会得出不同理解。
- 证据（33/40）：有具体操作路径示例（"进入集群 → 工作负载 → 自定义资源 → 编辑 ALBConfig……每次换证全网重复此类操作十几处"）与规模数据（150 台 VM、5 家云）。扣分：缺痛点量化——"换证频繁（付费证书周期短）且极易漏换"未给出证书存量张数、年换证轮次、历史漏换/事故记录；"极易漏换"是无数据支撑的断言，对以"漏换即事故"立项的提案，这是证据链的缺口。
- 紧迫性（27/30）：给出了延迟成本（"每延迟一轮证书周期就多承受一轮全网手工变更风险"），但同样停留在定性层面。

### 2. Solution Clarity: 113/120

- 具体性（38/40）：六个子能力均可向他人复述；换证流程给出完整链路（"变更清单 → 人工确认 → 批量执行 → 逐项进度 → 失败可回滚 → 变更后验证 → 变更报告"）。
- 用户可见行为（42/45）：happy path/边界/错误场景描述了运维视角的可观察行为（看板、清单确认、逐项状态、报告）。轻微扣分：变更向导的前端交互细节较薄（In Scope 仅一句"变更向导与报告"），且"人工确认"环节用户确认时看到什么信息（影响面摘要、分批策略）未描述。
- 技术方向（33/35）：两段式上传、���纹匹配、通道抽象、验证窗口等足以判断实现取向。轻微扣分：新鲜度阈值"（如超过 24 小时未完成新一轮扫描）"为示意值，最终阈值口径未定——提案阶段可接受，但进入 PRD 前需定值。

### 3. Industry Benchmarking: 109/120

- 方案引用（34/40）：4 个真实方案（Certimate、Certd、AllinSSL、阿里云证书托管）均附链接。扣分：全部为开源工具 + 单云托管服务，**缺企业级证书生命周期管理（CLM）商业方案对标**（Venafi / Keyfactor / EJBCA 类）。EV/OV 付费证书集中托管 + 引用关系管理正是企业 CLM 的核心品类，CTO 视角下该缺位使"自建"决策缺少与成熟商业基线的对照（哪怕结论仍是买不起/不适用，也应记录）。
- 替代方案（28/30）：含 do-nothing 在内 4 条，均为真实不同的路线，无稻草人。"混合：开源工具管续签 + e-cam 只做监控"是认真构造的中间选项。
- 诚实权衡（23/25）：自建路线如实列出"部署器需自研，工作量大，需分期"。扣分：开源路线的 Cons 中"无存量引用关系发现"成立，但"开源工具对 EV/OV 导入更换支持有限"（混合方案行）未给出依据（Certimate 实际支持导入证书部署，只是无发现能力），该处论证略仓促。
- 选择论证（24/25）：判定理由明确（"唯一能同时满足……"），且保留了 Challenge Override 记录，论证链完整。

### 4. Requirements Completeness: 97/110

- 场景覆盖（38/40）：happy/边界/错误三层齐全，且边界场景质量高（新旧证书并存、GitOps reconcile 回写、两段式中断态补偿）。
- NFR（31/40）：安全（私钥加密、内存解密、不落盘、审计、EIAM）、可靠性、及时性、可扩展性均已覆盖。扣分项：
  1. **平台自身作为全部私钥托管点的灾备/备份完全缺失**——若 e-cam 数据丢失且无异地备份，全部 EV/OV 证书私钥不可恢复（重新购买不恢复私钥），文档通篇无备份/恢复要求；
  2. 无容量/性能目标：证书张数、引用点规模、单轮扫描时长、批量变更并发度均未给出量级（问题段已知 5 云 + 150 VM，但方案未转化为规模约束）。
- 约束与依赖（28/30）：外部依赖逐项列出并标注就绪状态（"多云 K8s 集群接入凭证：待准备"），告警渠道确认被设为 PRD 前置依赖，处理规范。轻微扣分：K8s 凭证"待准备"未给出准备责任人/时限口径。

### 5. Solution Creativity: 89/100

- 超越基线（36/40）：引用关系自动发现确实是行业工具（自管部署型）不具备的能力，且差异化陈述克制（"其余为证书管理领域的标准做法……不另作创新声明"，避免了通胀声明）。
- 跨域借鉴（30/35）：TLS 主动探测借自可观测性实践（零侵入探活）；"变更后验证窗口 + 预期终态比对"借自发布系统的 canary/split-state 思想，属高质量迁移。扣分：可插拔执行通道是常规插件架构，借鉴密度不算突出。
- 洞见简洁性（23/25）：复用已有资产同步框架做只读发现是"为什么我没早点想到"级别的洞察。轻微扣分：指纹匹配 + 新鲜度阻断 + 验证窗口组合复杂度不低，对运维用户的认知负担未评估。

### 6. Feasibility: 80/100

- 技术（37/40）：依赖清单具体，最大不确定点（各云绑定 API 差异）已识别并转化为 PoC 任务。无明显 showstopper。
- **资源与时间线（17/30）**：整段仅"首期范围（双云部署器 + 全量监控）为可控的分期切分；阿里云、腾讯云证书 API 文档完善。具体估算在 tech-design 阶段给出"。无团队能力/带宽评估、无首期粗粒度工作量量级、无里程碑锚点。"可控的分期切分"是无依据的断言——11 项 In Scope 含 2 家云 4 类部署器 + 5 家云扫描器 + 前端 4 类页面，工作量主张需要至少量级支撑。估算细化可以留 tech-design，但"团队能否承担"属于提案级判断，完全缺席。
- 依赖就绪（26/30）：就绪状态诚实（K8s 凭证待准备、告警渠道待确认且设为门控）。扣分：两项未就绪依赖均无解决时间口径，无法评估是否阻塞首期。

### 7. Scope Definition: 75/80

- 具体性（29/30）：11 项 In Scope 均为可交付物。
- 明确延期（25/25）：Out of Scope 5 项逐条命名，且最难能可贵的是把"看得到却换不了"的运营窗口显式写进风险与范围。
- 有界性（21/25）：分期边界清晰，但首期无任何时间框架锚点（配合 Feasibility 的估算完全后置，团队无法判断这是 1 个季度还是 1 年的范围）。

### 8. Risk Assessment: 85/90

- 识别（28/30）：7 项风险均为实质风险，含 GitOps reconcile、孤儿证书配额这类深层运维风险。扣分：缺"平台自身故障/数据丢失导致私钥不可恢复"与"存量证书初始导入不全导致引用视图失真"两项。
- 评级（30/30）：L/H、M/H、M/M、H/H 分布诚实，未出现清一色"低概率高影响"。
- 缓解可执行（27/30）：缓解均为可落地动作（两段式统一设计、映射表补偿清理、PoC 前置）。扣分："二期排期与引用点增长绑定"无触发阈值，属方向性表述。

### 9. Success Criteria: 69/80

- 可测性（28/30）：��大多数指标客观可验（≥95%、≥99%、100% 阻断）。扣分："渗透式自查通过"未定义自查方法/通过标准，可测性弱于其他条目。
- 覆盖（19/25）：缺口——① 完整性"定时巡检"（In Scope 2）无验收标准（仅导入拦截有）；② 孤儿证书补偿清理（In Scope 7 / 风险表）无有效性指标；③ 执行通道可插拔性（In Scope 9，NFR 声明"新增部署器/通道不改上层流程"）无验证方式；④ 前端交付（In Scope 11）无验收口径。
- 内部一致性（22/25）：SC 集合整体可同时满足；扣 AMBIGUOUS-1（"旧证书已删除"与平台侧删除拦截的语义未区分）与 AMBIGUOUS-2（告警渠道门控只应用于到期告警 SC，TLS 差异告警与变更关联告警同样依赖渠道却未门控）各约 1.5 分。

### 10. Logical Consistency: 82/90

- 方案解决问题（31/35）：主链路成立，首期对华为/AWS/Azure 与 VM Nginx 的部分覆盖已显式声明并配兜底（"窗口期以到期看板 + 分级告警 + TLS 探测兜底提醒手工更换"）。扣分：问题段的三大痛点之一（150 台 VM Nginx 手工更换）在首期实质未被解决，"全网高危人工变更"仅消除约一部分；这是合理的分期，但 Solution 引言"一键批量更换"的闭环表述与首期实际覆盖面之间应更显式地打折表述。
- 范围↔方案↔SC 对齐（28/30）：发现 5 云/更换 2 云的边界在 Scope、SC、风险三处一致；扫描新鲜度阻断在方案/场景/SC 三处一致。扣分：SC-2 要求"覆盖 5 家云……与多云 K8s 网关 CRD"，而依赖段承认 K8s 凭证"待准备"——若凭证未就绪，SC-2 的 K8s 部分不可验收，但该 SC 未像告警渠道那样设置依赖门控。
- 需求↔方案连贯（23/25）：场景均映射到方案能力。扣分：约束"平台不能直连 VM Nginx"与方案 4 "对各子域名端点握手读取线上实际生效证书……无需接入服务器即可覆盖 Nginx 场景"之间隐含"全部 Nginx 子域名端点可从平台网络可达（公网/可路由）"的未声明假设；若存在仅内网解析的子域名，TLS 探测永久不可达，SC-8"不可达端点单独标记并告警"将产生持续性告警噪声，与"避免告警噪声淹没真实异常"的设计意图相悖。需在约束段声明可达性假设及内网域名处理口径。

## Phase 3 — Blindspot Hunt

1. **[blindspot] 文档正文残留机器校验输出**：Success Criteria 之后直接嵌入 `consistency_check_result: status: pass / pairs_checked: 36 / conflicts_found: 1`（proposal.md L207-210）。这是流程工具输出而非提案内容，出现在正文属结构性残留；其中"已通过改写措辞修复为可验证表述"指向的 SC 编号在当前文本中已不可考。应移除或移至 eval 元数据。
2. **[blindspot] 存量证书初始导入（bootstrap）无任何场景**：happy path 仅有"运维导入新购证书（PEM + 私钥）"。引用发现按指纹关联的前提是旧证书已入台账——现有全网在用证书的批量补录（证书文件从哪里来、私钥从原持有人处回收的流程、导入完整率如何度量）完全未提。初始导入不全则指纹关联失配，引用视图与变更清单从第一天起就带盲区，这直接影响方案核心价值的兑现速度。
3. **[blindspot] 全网高危变更仅单人确认，与问题自身的风险叙述冲突**：问题段称每轮换证是"全网高危人工变更"，方案以"一键批量 + 人工确认 + 可回滚"化解，但 Out of Scope 明确"更换前的多人审批流（首期为单人确认）"。单人即可触发覆盖 2 家云 + 多集群 K8s 的批量生产变更，职责分离（发起/确认分离）在首期即缺席，且无补偿控制（如分批灰度上限）说明。作为风险决策可以接受，但提案未论证为何单人确认 + 回滚足以覆盖误操作/恶意操作风险。
4. **[blindspot] 验证窗口与回滚保护期的参数交叉未定义**：删除规则引入"回滚保护期"（"处于回滚保护期内的证书禁止删除"）与"变更后验证窗口"（"有限时长的验证窗口"）两个时间窗，但两者的时长、相互关系（验证窗口结束是否即保护期结束）均未给出任何口径，且无一条 SC 覆盖保护期行为。属新引入概念未闭环。
