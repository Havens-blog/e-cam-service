# Proposal: 日志查询体验全面优化(接口性能 + 排版 + 功能)

## Problem

日志查询页(纯前端 + e-cam-service `/logs/*` 接口)存在三组明显缺陷:接口响应慢(典型实测 `GET /logs/sources?log_type=waf` 接近 20 秒)、页面等待/失败反馈缺失(20s 白屏无任何回馈)、明细与筛选交互粗糙(无快捷值、无图表下钻、多源结果不可折叠)。

### Evidence
- 用户实测:`http://localhost:8888/api/v1/cam/logs/sources?log_type=waf` 响应接近 20 秒(历史曾优化到 ~0.37s,当前退化,疑为缓存冷启动/并发退化/热重载窗口叠加)。
- 页面在 `search` 执行期间只显示骨架(shimmer),长时间无文字进度;失败仅弹系统错误串。
- 明细表不分源组织,多云 WAF 84 个源(71 Akamai + 13 国内)结果混排;TopN 图与明细无联动;字段筛选需手输值(状态码/IP/域名无快捷回填)。

### Urgency
接口秒级延迟是本轮最高频投诉;20s 的查询会让用户误以为系统不可用而重复点击/放弃。缺陷成本每日叠加,且影响面是全功能入口。

## Proposed Solution

性能与体验分四条线交付:

1. **接口响应优化(后端)**:先复现 `sources` 20s 的根因(测量各 provider 阶段耗时),定向优化——三层缓存(域名枚举/前缀/logstore)已有,排查退化点(缓存失效、并发上限、Akamai activeDomains SQL 串行、AWS 前缀冷启动),必要时加**进程级预热**与**跨请求缓存命中率日志**;search/aggregate 冷启动同治理。
2. **加载等待态 + 失败重试(前端排版)**:冷查询显示明确"正在查询 N 个云账号…"步骤态与耗时,失败给可点重试 + 具体原因;截断/超时给明确的降级说明。
3. **图表栅格/明细自适应(前端排版)**:统计区三图+趋势栅格按内容自适应;明细分屏滚动、表头吸顶;图表高度随分组数微调。
4. **功能增强(前端)**:a) 字段筛选取「快捷值」——从当前样本回填常见值(状态码集合/热门域名/动作枚举)点击即填;b) 结果区「按云·账号折叠分组」展示明细,组头显示条数/耗时;c) TopN 条形图点击某项 → 自动为该分组值加字段筛选并重查。

### Innovation Highlights

- 性能治理以「可测回归」为准:`curl -w` 实测热/冷缓存耗时并写入 SC,避免"凭感觉变快"。
- 快捷值回填利用**已返回样本**(零额外请求),把自由输入降维成点选,贴合运维高频路径(看 404、找攻击源)。
- 图表 ↔ 明细联动把"看到异常(top N)→ 钻到具体日志"合并成一次点击,这是日志工具(Uber 日志查看器/Grafana Loki)的标准心智,在本站作为统一字段筛选复用。

## Requirements Analysis

### Key Scenarios
- 用户选 WAF 类型进页面 → `sources` 应热缓存 <300ms、冷 <3s;80+ 源清单不白屏。
- 查询途中网络慢/AWS 扫描慢 → 页面显示进行中状态与已耗时,不显示"死屏";某源失败只标该源,不整页失败。
- 用户想按某 IP/状态查明细 → 从样本下拉/点击 TopN 图填充筛选,一键重查。
- 多云结果 → 按账号折叠,展开某账号看其域名/条数/错误。

### Non-Functional Requirements
- 性能:`GET /logs/sources`、`POST /logs/search`、`POST /logs/aggregate` 热缓存(10min 内)<300ms,冷启动 <3s(以 curl 实测为准;冷定义=进程内缓存清空后首次)。
- 兼容:保持 `/types` 字段字典驱动动态列不变;不破坏现有 URL/参数契约。
- 可访问性:状态/失败信息必须文本化(非仅颜色),等待态有 `aria-label`。

### Constraints & Dependencies
- 后端缓存为**进程级**(10min TTL):实测目标依赖单一实例假设(dev 下成立)。
- SLS `检索|SQL` 扫描计费:不得为提速而逃避过滤语义;域名枚举 SQL 不得放大扫描量。
- AWS S3 前缀列举/扫码慢是物理延迟,冷启动目标靠缓存+预热达成,不引入请求级 hack。

## Alternatives & Industry Benchmarking

| Approach | Source | Pros | Cons | Verdict |
|----------|--------|------|------|---------|
| Do nothing | — | 零改动 | 20s 延迟持续,用户流失 | Rejected:已是最高频投诉 |
| 只调大缓存 TTL | 本地 | 一行改动 | 治标不治本,冷启动依旧;TTL 过大导致域名变化不感知 | Rejected |
| 请求级并发扩张(SLS 扇出 8→16) | 本地 | 可能降延迟 | 会放大扫描量与计费,SI 风险 | 视测量结果小步采用 |
| 后台预热 + 缓存命中日志 + 阶段耗时统计 | 可观测标准路径 | 冷启动/退化都可根治,测得见 | 需少量埋点 | **Selected:先测量再动** |

## Feasibility Assessment

### Technical Feasibility
全栈均为现有代码(Go provider 缓存 + Vue 页面),无新技术依赖。阶段耗时在 provider 层已有 `DurationMs`,sources 需补各 provider 明细。

### Resource & Timeline
单人(本会话)交付;/quick 小特性,预计 4~8 个任务,按性能→排版→功能并行拆分。

### Dependency Readiness
无外部依赖变化;所有云凭证可用(dev 环境已联通 SLS/LTS/S3)。

## Risks

1. **性能根因是冷启动/热重载窗口**(环境噪音):表现为 20s 但真实原因是 dev 重启期间请求积压。缓解:复现时先固定服务进程状态,用连续两次请求区分热/冷;SC 按冷/热分别验收。
2. **S3 前缀列举物理慢**,冷启动 <3s 可能整体不达标(WAF 71 源)。缓解:SC 拆分为「进程内已缓存的源 <300ms」+「冷启动显式标注并预热」;若 AWS 拖累整体,将 AWS 源冷启动目标放宽并单独报告。
3. **布局改动破坏既有交互**(图表下钻误触)。缓解:改动集中在新增交互,不重排既有控件;下钻后可一键清除筛选回原位。
4. **AKamai activeDomains SQL 每源 ~1.5s 串行**:若为 20s 主因,改并发需保证 SQL 扫描量不放大。缓解:复用现有域名缓存,只并发化首次枚举。

## Success Criteria

- [x] 复现并定位 `GET /logs/sources?log_type=waf` 20s 根因(环境噪音或代码退化,至少区分)
- [x] `curl` 实测三个接口:热缓存 <300ms、冷启动 <3s(AWS 源单独报告,不阻塞整体 SC)
- [x] 查询期间显示进行中状态(云账号数/已耗时),失败可重试且错误可读
- [x] 明细区按云·账号可折叠分组,组头含条数/耗时
- [x] 字段筛选取值支持从样本回填快捷值(至少 状态码/域名/动作)
- [x] TopN 分组图点击项 → 自动加字段筛选重查,可一键清除
- [x] vue-tsc / eslint / go build / go test 全绿;行为回归(搜索/聚合/翻页不受影响)

## Out of Scope

- 除上述四项外的其它排版审美重构(字体/间距全改)
- 聚合维度/指标的再次扩展、深翻页(时间游标)语义变更
- 服务端分页/游标协议重设计
- 日志类型、字段字典的新增
