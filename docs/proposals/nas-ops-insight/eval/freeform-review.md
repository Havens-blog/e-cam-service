# Freeform Expert Review

**提案**:多云文件存储 NAS 经营洞察(容量/使用率指标)
**审查专家**:多云存储监控指标架构师(Multi-Cloud Storage Monitoring Metrics Architect)
**审查日期**:2026-09-17

## Background Assessment

我理解这份提案要解决的是一个「有能力枚举、无经营视角」的缺口:平台已经能同步 5 家厂商的 NAS 文件系统,但缺少容量/使用率的水位趋势,运营无法判断扩容时机,而资产表里的 `capacity/used_capacity` 字段实盘质量差(华为/AWS 为 0、aliyun used=1 明显失真),不可用作任何决策依据。提案给出的解法是平移一条已被 CDN 验证过的指标链路:新增可选的 `NASMetricQuerier` 接口,5 家厂商各自实现(aliyun CMS、tencent monitor、huawei CES、volcengine cloudmonitor、aws CloudWatch),采集执行器 `nas:collect_metrics` 把天粒度指标写入 `ecam_nas_metric`,唯一键 `(account_id, fs_id, date)`;同时引入持久化日闸 `scheduler_state` 替换 CDN 的内存 `lastMetricsCollectDate`,一次解决服务重启重复提交的遗留缺陷;前端补上 NAS 抽屉「监控」tab 趋势图与列表页运营卡。

我特意核对了代码库,确认提案所称的 CDN 模板是真实存在的:CDN 侧有 `CDNMetricQuerier` 可选接口(interfaces.go)、`SyncCDNMetricsExecutor` 执行器、以 `(account_id, domain, date)` 为唯一键的 `ecam_cdn_metric` DAO、以及挂在分钟级检查循环上的调度触发器 `checkMetricsCollection`(auto_sync_metrics.go)。CDN 的内存闸缺陷也确实如提案所述——`lastMetricsCollectDate` 只在进程内存里推进,重启归零,`shouldTriggerDailyMetric("")` 恒真,于是重新提交当日任务。

整体上,提案定位清晰、范围收敛、以已验证模板为基底,风险自评也基本诚实(volcengine 指标名、华为 namespace 是最大不确定项)。但我的判断是:恰恰是在 CDN 模板**不能**直接平移的地方,提案欠了足够的规格——单位语义、日快照取值口径、跨账号共享 fs 的聚合口径、『空结果』的可观测性。这些是下文风险审查的主线。

## Key Risks

跨厂商指标语义一致性是这条链路的地基,而提案在地基上留的空白最多。字段定义了最终单位,却没有定义到达该单位之前的每一跳转换:

风险：容量/使用率的跨厂商单位归一化完全未定义,新表可能复刻旧表同样的单位失真。
> "NASMetric 字段:`fs_id / date / capacity(GB) / used_capacity(GB) / utilization(0-1, used/capacity)`"
提案只声明了字段的最终单位是 GB,却没有一张「各厂商监控 API 原始返回单位 → GB」的归一化对照表。而证据本身已经暴露了问题根源——"aliyun `capacity=10485760, used_capacity=1`(used 明显失真)":10485760 是字节口径(10 MiB)而非 GB,说明现行 `sync_nas.go` 链路就是把厂商返回的 Bytes 直接写进了注释为 GB 的 `NASInstance.Capacity` 字段。若新的指标适配器沿用这份想当然的映射,`ecam_nas_metric` 会用「新表装旧数据」的方式复刻提案声称要修复的数据质量 bug。后果是经营洞察建立在错误数量级之上,扩容判断被真实值误导,而问题陈述里那句"数据不足以支撑运营决策"会原样延续到新表。

风险：`utilization = used/capacity` 在当前实盘数据状态下必然除零,used>capacity 的瞬时越界也无任何处理约定。
> "utilization(0-1, used/capacity)"
证据里正是 "huawei `capacity=0, used_capacity=0`,aws `capacity=0, used_capacity=0`"。capacity=0 时算使用率必然除零,collector 可能 panic、写脏值或整行跳过。而状态型瞬时快照下 used>capacity 完全可能发生(厂商指标刷新时点不一致、扩缩容边界、计量口径差异),提案对这两个边界没有任何策略。后果:两个"主力厂商"(华为/aws)的首日采集可能全部失败或产出 NaN,而且会被『尽力而为返回空』笼统吞掉,极难定位。

风险：状态型「每日快照」的采集时刻与取值口径未定义,与"判断扩容时机"的使用场景并不自洽。
> "指标语义为状态型(capacity/used/utilization)而非 CDN 的流量型——每日快照即可表达存储水位,NAS 天然适合天粒度"
"每日快照"没有定义取哪一点:日界(00:00)末态、当日峰值、还是厂商末日聚合值?若是凌晨调度取「今日」,00:00 附近数据点稀疏且各厂商监控指标有聚合延迟(CloudWatch/CES 都有分钟级延迟),取到的今日值约等于昨日末态,恰恰掩盖了运营最关心的当日高水位。CDN 模板对同类问题是有明确处理的——调度器注释 "days=2:凌晨补采时「今日」行只有约 1 小时数据,必须连昨日完整数据一起采集"(auto_sync_metrics.go),而提案对 NAS 的采集窗口(几点触发、写昨日完整行还是今日部分行)只字未提。对"是否需要扩容"这类判断,快照取在低点会系统性漏报尖峰。

尽力而为容错是这套架构吸收弱厂商不确定性的手段,但提案把它用成了没有仪表盘的安全气囊:

风险：『尽力而为返回空』缺少失败可观测性,「适配器失效」与「真实无指标」在空结果上不可分辨。
> "弱厂商尽力而为,失败/指标名未知返回空,不阻塞全流程"
Scope 与成功标准里没有任何失败计数/结构化日志要求,成功标准只写 "volcengine/tencent/aws 无数据时不报错、不阻塞(尽力而为语义:单厂商失败仅自身空)"。若适配器内部吞掉异常返回空(aws 更是被明文允许「若不可行返回空」),运营看到的空态与「真实无指标」完全相同。更隐蔽的是,若执行器照搬 CDN 模板的『当日无数据不写库』过滤(sync_cdn_metrics.go 中 `m.Bytes == 0 && m.Bandwidth == 0 && m.HitRate < 0` 则 skip),华为/aws 的全零行会被直接丢弃,空表让问题更不可见。后果:一次采集链路静默失效可能持续数周,直到某天运营发现该厂商水位从未更新,而那时历史缺口已经补不回来。

持久化日闸是提案的创新点,但它的失败降级方向恰好与自身主目标相冲突,这是我审阅中最扎眼的一处:

风险：日闸「写失败记录日志」的降级,会让提案要修的核心缺陷(重启重复提交)在写失败时原样回归。
> "读失败按「上次日期未知」触发一次(安全侧);写失败记录日志"
提案要消除的是 "今天实测发现服务重启会重复提交 25+ 条待办指标任务"。若 00:10 采集成功但日闸写入 MongoDB 失败(仅记日志),内存日期虽已推进、持久层仍是昨日;02:00 服务重启读到昨日日期 → 判定跨日 → 重新提交当日任务。这与成功标准 "服务重启后当日不再重复提交 NAS/CDN 指标采集任务" 直接冲突。把"重启幂等"押在一条没有重试、没有告警、失败即丢的写路径上,等于把核心卖点建立在最薄弱的一环。

风险：日闸读失败「触发一次」在分钟级调度循环上不可执行,可能逐分钟洪泛任务队列。
> "读失败按「上次日期未知」触发一次(安全侧)"
日闸检查挂在调度器分钟级循环上(CDN 触发器即"挂在 AutoSyncScheduler 的分钟级检查循环上",NAS 执行器"仿 sync_cdn_metrics.go")。若 MongoDB 持续不可用,每次检查读到「未知」都触发提交,而"触发一次"的"一次"没有载体——内存日期从未被写入,读失败又无退避窗口,结果是每轮循环都提交。指标表写入同样依赖 MongoDB 也会失败,采集白跑,厂商 API 配额被白白消耗,任务队列被同质任务灌满。

风险：日闸「按资源类型分键」只隔离 cdn/nas 两份状态,不隔离并发触发(多副本、手动+自动重叠)。
> "日闸按资源类型分键(cdn/nas 独立)"
这个缓解只解决了 CDN 与 NAS 共享同一调度循环时状态键互相覆盖的问题,没有解决同一 NAS 采集被并发触发的问题:滚动重启时新旧进程短暂并存、或用户手动触发 `nas:collect_metrics` 与每日自动任务重叠,都会让同一账号的厂商 API 被并发调用。CDN 执行器靠进程内 `syncingNow` 账号互斥("同一账号同时只放行一个采集任务,避免重复消耗厂商 API 配额")防重叠,但那是内存态,跨副本无效。对 AWS CloudWatch 这类有严格 GetMetricData 配额的 API,重复调用直接撞配额、产生额外成本。

厂商取舍与聚合口径上有两处自相矛盾:

风险：aws 被允许「返回空」与问题陈述里的 aws 数据质量 bug 互相矛盾,aws 的容量失真可能永不被修复。
> "aws(CloudWatch,需新增依赖,**已有主动放弃先例**——若不可行返回空不阻塞)"
但 Urgency 明确写 "华为/AWS 容量字段为空是现成的数据质量 bug,越晚修,历史水位缺失越多"。若 aws 允许返回空,aws 的 NAS 在经营视图里将永远空态,原问题对 aws 一项未解决。「已有主动放弃先例」来自 CloudFront 场景,而 CloudWatch 对 EFS 有标准指标(StorageBytes 等),NAS 并非不可行——把 CloudFront 的结论前置套用到 EFS 缺少论证。这是 Problem 与 Solution 之间的逻辑裂缝,需要在提案里做出明确取舍,而不是含糊两可。

风险：运营卡/ Top 的跨账号同 fs 聚合口径未定义,同一物理文件系统会被重复计数。
> "多账号同 fs_id 并存(多活/共享实例)各账号独立保留(复用 CDN 多账号键经验)" 与 "列表页顶部加运营卡(总容量/已用容量/平均使用率,仿 CDN 近2日卡)"
CDN 的 Top 聚合暗含"域名只归属一个账号,账号间不会重复计同一域名"的前提(asset_cdn_query.go 注释),而 NAS 提案恰恰相反,主动允许同 fs_id 跨账号并存。那么「总容量/已用容量」若跨账号求和,共享的物理容量被双计;"平均使用率"跨实例平均时,无数据实例按 0 参与还是跳过,也未定义。成功标准 "≥3 账号同 fs 各留一行 live 测试" 证实并存是预期行为,但聚合口径(去重 or 求和)缺失,运营卡的数值会系统性虚高,Top 排序也会失真。

接口契约与前端字段映射上的规格缺口:

问题：读取接口的账号隔离未定义租户校验,account_id 直接来自客户端参数,存在越权面。
> "GET /assets/nas/metrics?fs_id=&account_id=&days="(按账号隔离,仿 CDN 读取) 与 NFR "读取接口按账号隔离(tenant → accounts → filter),防跨租户越权"
提案把 account_id 放进查询参数,却没说它如何与调用者租户绑定。CDN 读取侧根本不接收 account_id,而是从鉴权上下文取 tenantID,再"先取租户全部云账号 → 逐账号过滤查询"实现隔离(asset_cdn_query.go)。NAS 若直接信任客户端传的 account_id,一个租户可以传其他租户的 account_id 读取对方指标。服务端必须校验 account_id 属于该 tenant 的账号集合,否则"防跨租户越权"只是声明而没有落点。同理,Top 排序字段("容量或使用率")、回看天数、以及"最新一天 vs 近 N 天均值"的口径,都还没有定义。

厂商不确定性的计划内收敛,是提案自评里最诚实的一段,却恰恰是落地时最容易滑掉的一段:

风险：volcengine/华为探测仍停留在「运行时实测」的口头兜底,未进入任务清单与截止判定。
> "volcengine 监控指标名无公开文档,需运行时探测(最大不确定性)" 与 "华为 SFS Turbo 的 CES namespace(SYS.SFS_Turbo)与容量指标公开度需运行时验证",Feasibility 中 "风险集中点:volcengine 指标名实测、华为 namespace 验证——均走「尽力而为返回空」兜底"
Next Steps 只有 "Proceed to `/write-prd`",没有列出「探测任务 + 截止判定 + 验收标准」的显式条目。作为最大不确定项(且直接决定 5 家中 2 家是否有真实数据),把"实测"留作实现期口头兜底,极容易变成上线时静默返回空、二期无限延期的状态。另外,华为一侧被简化为 `SYS.SFS_Turbo` 一个 namespace,而资产模型覆盖 standard/extreme/cpfs 多种文件系统类型,华为普通 SFS 与 SFS_Turbo 的 CES namespace/指标集不同,适配器需按类型分别探测,不能一刀切。

风险：华为「单 region 静默回退 cn-north-4」列为单独件,但指标采集若复用同一 region 解析会查错地域。
> "华为 SFS 单 region 静默回退 cn-north-4 隐患修复——单独件"
该隐患列为 Out of Scope 可以接受,但指标查询依赖实例的真实 region;若 huawei 指标适配器复用带此回退的 region 解析逻辑,非 cn-north-4 实例会查错地域 → 返回空或跨地域错误数据,且与「真实无指标」混同无法分辨。提案至少应声明指标采集路径独立于该回退逻辑,否则会把一个已知 bug 静默带进新链路。

最后,唯一键幂等语义在状态型指标上的迁移还有一个被忽略的偏差:

问题：状态型快照沿用 CDN「同日重采覆盖」的 upsert 语义,会使每日值在同日重采时不确定。
> "唯一键幂等 upsert" 与 "同账号同日 upsert 幂等"
CDN 的 DAO 注释明确"同日重采覆盖为最新值"。若 NAS 沿用覆盖语义,日闸读失败触发、手动重跑、或多副本并发,都会在同日内以不同时刻的快照覆盖同一行——「今日」的 capacity/used 取决于最后一次写入的时刻,趋势上同一日数值会反复跳变。对 CDN 流量型指标,重采覆盖是"补全"语义,合理;对 NAS 状态型快照,它让"每天一个值"变成"每天最后一个碰巧写到的值"。唯一键只保证不产生脏行,不保证日值稳定,这个区别提案没有意识到。

## Improvement Suggestions

按影响排序,我建议提案在进入 `/write-prd` 之前先补上以下规格,每一项都对应上文一个或一组风险:

建议：新增「单位归一化与字段语义」专节,把每一跳转换写死。
Addresses:容量/使用率跨厂商单位失真、utilization 除零/越界。
> 为 5 家厂商各列一行「监控 API 返回单位 → GB 换算」对照(如 aliyun CMS NAS 指标按字节、huawei CES 按字节、CloudWatch StorageBytes 按字节、volcengine 实测确认),并规定 capacity=0 时 utilization 记 0 或空值、used>capacity 时按 min(used,capacity) 收敛并打日志。建议 utilization 不作为独立落库字段、改由读取时从 capacity/used 派生,避免重采时三字段不一致。采纳后,`ecam_nas_metric` 的每一行都能在审查时反向验证数量级正确,新表不会再复刻旧表的单位 bug。

建议：定义日快照的取值口径与采集窗口,并加一次性历史回填任务。
Addresses:日快照采集时刻/口径未定义、状态型同日重采覆盖导致日值不确定。
> 明确写死三点:(1) 每日值是日界末态还是当日峰值——若服务于"扩容时机",应明确取峰值或至少说明取末态的取舍;(2) 调度时刻与采集区间,建议对齐 CDN 的 days=2 思路(补昨日完整行+今日初态),并避开各厂商指标聚合延迟窗口;(3) 同日期行采用「首写生效」或保证单日单次采集,让日值不可变。同时加一个一次性回填任务,从厂商 API 拉取启用日前 N 天历史(各厂商一般支持近 14~90 天),否则运营要等 N 天才能看到 30 天趋势,与 Urgency 里"越晚修,历史水位缺失越多"的自省相悖。

建议：为「尽力而为返回空」配上失败可观测三件套。
Addresses:空结果无法区分「适配器失效」与「真实无指标」。
> (1) 执行器按厂商/账号维护失败计数与最后一次错误,任务 Result 里带上(CDN 已有 `skipped_providers` 雏形,扩展为含错误明细);(2) 每个适配器区分「探测不支持」与「调用失败返回空」两类路径,前者打 INFO、后者打 ERROR 并带 error 字段;(3) 前端空态区分"无数据"与"采集失败/未启用",运营卡在采集异常时显示警示而非纯空。采纳后,一周无人察觉的静默失效会变成当天可见的告警。同时明确 NAS 执行器**不要**继承 CDN 的"当日全零即跳过"过滤,让 capacity=0 的异常行落库可见。

建议：日闸改为「原子认领 + 写失败重试/告警 + 读失败退避」。
Addresses:日闸写失败仅记日志、读失败洪泛、并发触发无原子认领。
> 用一次 `findOneAndUpdate`(条件 `resource_type=nas AND last_date < today`,更新为 today)原子认领当日,多副本同时触发时只有一个成功;认领成功后才提交采集任务。日闸写入失败走重试(带指数退避)并升级为告警,而不是仅记日志;读失败设置最短退避窗口(如 5 分钟)再重读,防止分钟级循环洪泛。这样写失败时重启的重复提交、读失败时的任务洪泛、多副本/手动重叠的并发调用,三个场景都被同一个机制兜住。

建议：把 aws 的取舍与运营卡/ Top 的聚合口径一次性定死。
Addresses:aws 空结果与问题矛盾、跨账号同 fs 重复计数。
> 二选一并写进提案正文与成功标准:要么把 aws CloudWatch(EFS StorageBytes)列为必达项并进验收,要么把 aws 从"数据质量 bug/urgency"中显式摘除、降级为"二期补齐"。同时定义运营卡与 Top 对共享 fs 的聚合规则:按 fs_id 去重后计数(多账号取其一)还是按账号分别展示,以及"平均使用率"对无数据实例是跳过还是记 0。CDN 的 Top 聚合前提在 NAS 不成立,这个差异必须显式处理。

建议：补全读取接口契约,租户校验下沉到服务端。
