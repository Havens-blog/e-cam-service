# 自主迭代操作教训汇编（2026-11-05/06 会话）

> 来源：统一审计日志专项（SDK → e-cam-service → e-iam → 前端 → 联邦设计）约 15 轮迭代的实测教训。
> 每条按「现象 / 根因 / 规则」三段式沉淀，供后续迭代与会话参考。

## 一、脚本化编辑的静默失败（本会话三次踩坑，最高频）

| # | 现象 | 根因 |
|---|---|---|
| 1 | `str.replace()` 无匹配静默 no-op，打印「成功」但文件未变 | 锚字符串缩进/内容与实际差一个字符 |
| 2 | PowerShell here-string 与 `Set-Content -Value` 混用管道 → 脚本文件写坏/未写盘，node 仍跑旧内容 | 管道输入与 -Value 参数绑定冲突 |
| 3 | `git add -A` 把提交信息暂存文件（.m2.txt/.m14.txt）带进提交 | 显式列表意识缺失 |

**规则**：
1. **任何脚本化编辑后必须回读验证**（读回文件断言关键内容真的存在/消失）。
2. 小改动直接用结构化编辑工具（带系统级回读），不走临时脚本。
3. 提交前 `git show --stat` 自查文件清单；临时文件用显式列表 add。

## 二、验证判据的「中间件先答」陷阱（两仓库各一次）

| 现象 | 根因 |
|---|---|
| :8001 无凭据探测 401 被误读为「路由存在」 | e-cam 全局鉴权中间件先于路由匹配，对一切未认证请求（含不存在路由）返回 401 |
| :9000 新路由 403「路由未注册权限元数据」 | e-iam 权限中间件同样先于路由匹配（不存在路径同文案） |

**规则**：探测结论必须打到**唯一能区分目标状态的层** —— 用带会话请求（404/200 可区分路由存在性）；或用「已知存在/已知不存在」的对照样本锚定判据。**工具给出否定答案时，先验证工具自身的前提**（例：goimports 不带 `-local` 参数误报 clean；模块直查不带 base 前缀拿到 HTML 回退）。

## 三、格式化与生成链的「本地/CI 对齐」

| 现象 | 根因 |
|---|---|
| 本地 `gofmt -l` clean 但 CI 报未格式化 | 工作副本 CRLF（autocrlf）污染判断；或本地 gofmt 版本差异 |
| 本地 `goimports -l` clean 但 CI 报违规 | CI 的 goimports 带 `local-prefixes`（本仓库 import 须独立成组且置于末组），本地未带该参数 |
| 生成链一致性红：permissions.md 标题漂移 | permgen 把**检出目录名**烧进文档标题 —— worktree 路径泄漏（已在 e-iam#7 治本：改从 go.mod module 推导） |

**规则**：
1. 本地校验命令的参数必须与 CI 完全一致（`goimports -local github.com/Havens-blog/<repo>`；gofmt 用 LF 副本验证规避 CRLF 伪影）。
2. 在 worktree 里跑生成链后，**diff 生成产物找「非本次改动的漂移」**——路径/时间戳/环境名泄漏是生成链误报的主要来源。
3. 生成器从环境推导的内容（目录名、时间戳）是确定性敌人：能固定的固定，能从代码事实（module 路径）推导的从代码推导。

## 四、CI lint 的「责任边界以包为单位」

- 现象：PR 的 `--new-from-rev` lint 报出**并行会话在同一个包里新加代码**的违规（change_handler.go 魔法数）。
- 规则：接入他人包时，**整包的 lint 债一起清**（基线按包不按行）；反过来，自己往包里加代码也别指望「我只改我的行」。

## 五、跨层/跨仓库协作的边界意识

| 教训 | 说明 |
|---|---|
| 分层合规是冲突避雷针 | e-iam 读侧端点按 AGENTS.md 分层（映射在 Repo、DAO 纯 GORM）恰好**零 wire_gen.go 改动**，与并行 WIP 零冲突；图省事走 wire 注入就会正面相撞 |
| 后端能力先行，前端消费缺位 | `total=-1` 降级契约落地时无 UI 消费者，两年后数据涨到 540 万行才暴露 —— **后端契约 PR 合并时应同步检查前端消费面（含错误/降级语义）** |
| 给既有链路加入口，顺链路走特殊分支 | #288 的 field_name 筛选让 total=-1 路径变得易达，从而暴露 UI 缺陷（→ e-cam-web#292 修复）|
| 无索引论断先查实际索引清单 | 「field_name 无索引必超时」的论断与 #382 已补的复合索引矛盾 —— 并行会话补的索引不会在任何提示里出现，**结论的时间戳要核对** |

## 六、双写设计的暗礁

- **幂等命中不重复双写**：RecordDedup 的 `inserted=false` 意味着旧存储认为事件已存在，此时仍向统一集合 Emit 会造成两套存储语义漂移。
- **空去重键在 MySQL/SQLite 唯一索引下互相冲突**（空串≠NULL），逐条降级静默跳过 = 数据丢失 —— 指针化（空→NULL）修复；Mongo 侧用 `bson:"...,omitempty"` + 稀疏索引规避（e-iam#6 附带修复，回归测试锁死）。
- **双写的每条路径都要问**：「旧存储的这个返回值对统一集合意味着什么？」

## 七、等待点的处理

- **候选池耗尽时不硬凑工作**：如实报告等待点，把等待项的成本降到最低（例：部署管道断裂 → 产出逐仓逐名的 Secrets 修复清单 #445）。
- **把一次性手工修正升级为机制修复**：permissions.md 标题漂移手工改一行是治标，permgen 改为 module 推导是治本（e-iam#7），表驱动测试锁死。
- **「等待决策」的两种状态**：材料不存在（永远等不到）与材料备齐（一次评审解决）—— 产出结构化的决策材料（#441 联邦设计：现状/对比/安全要点/分期/待决策点）是等待期能做的最有效推动。
