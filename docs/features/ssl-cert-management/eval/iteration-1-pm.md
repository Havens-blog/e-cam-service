## Phase 1 — 推理审计（跨文档一致性）

### 发现 1（严重）：部分失败路径与验证窗口的关系，流程图 ↔ 正文 ↔ 用户故事三方矛盾

- Mermaid 图（prd-spec.md L110-122）：`N{全部成功?}` 仅在"是"分支进入 `V[验证窗口]`；"部分失败"分支 `N -->|部分失败| O[失败项保留旧引用 可一键回滚]` 直接走回滚 → `U[变更报告]`，**全程不经过验证窗口，也不进入回滚保护期**（保护期只出现在 `X` 节点，即全成功分支）。
- 但 spec 正文 In Scope（L55）："窗口内 TLS 探测按变更清单预期终态（**含部分成功的分裂状态**）比对"——明确说部分成功也要进验证窗口。
- prd-user-stories.md Story 3 AC5（L67-69）："Given 变更完成进入验证窗口（2~24 小时）……（**含部分成功分裂状态**）"——同样要求部分成功进窗口。
- 结论：图与文字/故事对"部分失败是否进验证窗口、是否进入回滚保护期"给出相反答案。按扣分规则记 **-30（跨节冲突）**，计入 Flow Diagrams 维度。

### 发现 2（严重）：回滚对象错位——"对失败项回滚"在语义上自我矛盾

- spec L63（Story 3 AC3 同）："**失败项保留旧证书引用**、成功项正常完成"。
- 同文档 Story 3 AC4（L64-66）："对**失败项**执行回滚 → Then 回滚**恢复旧证书引用**"——失败项的旧引用根本没被改过，"恢复"无从谈起。
- Mermaid `O[失败项保留旧引用 可一键回滚]`、prd-ui-functions.md UF-4 第 4 步（L187）："**失败项**出现'回滚'操作"——四份口径全部把回滚按钮放在失败项上；而真正切换到了新证书、在部分失败时需要回退以恢复一致性的**成功项**，反而没有任何一处 UI 操作或故事覆盖。
- 这是一个跨全部三份文档的统一逻辑错误（不是文档间冲突，而是各自内部自相矛盾），计入 User Stories（AC 可验证性）与 Edge Case（失败恢复语义），并在盲区段单列。

### 发现 3（中）：spec 功能项 ↔ UI 功能 ↔ 故事三向对齐缺漏

- Story 4 AC3（L86-88）"补传私钥……升级为完整托管"——prd-ui-functions.md 五个 UF 中**没有任何补传私钥的交互流程或入口**（UF-1 只有导入/删除/发起更换）。
- spec In Scope（L56）"GitOps/控制器管理的目标标记'不可自动变更'并**单列清单**"——ui-functions 与 user-stories 中均未出现该清单的任何展示或故事。
- spec（L56）"第二段失败时依据映射表**补偿清理未绑定的云侧孤儿证书**"——变更报告字段（UF-4 L196：清单、逐项结果、回滚状态、验证结论）不含孤儿清理结果，用户无法感知补偿是否发生。
- 记入 Functional Specs（交互完整性）与 Scope Clarity（范围一致性）。

### 发现 4（中）：导入时 SAN 校验基准未定义

- Story 1 AC（L17）拦截条件含"**SAN 不含预期域名**"；UF-1 校验规则（L80）为"SAN 解析"；spec Flow 步骤 1（L76）"系统校验（私钥匹配/证书链/**SAN**/有效期）"。
- 但 spec 自己定义的 SAN 基准是"**引用资源所服务的域名集合**"（L49、L187）——新导入证书尚无任何引用资源，导入时刻的"预期域名"是什么无从得知。AC 不可客观验证，校验规则不可执行。

### 发现 5（轻）：其他核对项（未达扣分阈值或已折入维度分）

- 状态机：spec 含"→ 关闭"，UF-4 状态枚举漏"关闭"（折入 Scenario 一致性）。
- 只读查看者可达页面："仅可见'到期看板'一级入口；台账对只读者隐藏操作按钮"——若台账不在导航内，"隐藏操作按钮"针对什么场景（直连 URL？）未说明（折入 Scenario 隐式假设）。
- 分批"单批不超过总量一半"对奇数清单的取整规则未定义（折入 Edge 边界）。

## Phase 3 — 盲区猎杀（[blindspot]，均含引文，均在评分维度之外）

1. **[blindspot] 分批灰度的剩余项生命周期无主** — spec L79"工程师人工确认（支持分批：单批不超过清单总量一半）→ 批量执行"。首批 50% 执行完进入验证窗口/保护期后，剩余 50% 是同单续批、另开新单、还是复用同一清单？三份文档均无答案。而分批是 Out of Scope 中替代审批流的第一道安全机制（L67"分批灰度"），其自身语义不完整会直接削弱"单人确认"的论证基础。

2. **[blindspot] 回滚操作放在失败项上，成功项无回滚入口** — UF-4 L187"失败项出现'回滚'操作"配合 spec L63"失败项保留旧证书引用"。部分失败时真正处于"新证书已上线但期望回退"状态的是成功项，UI 上却没有对应操作；按现有四份口径实现，会出现"按钮在不需要回滚的项上、需要回滚的项上没有按钮"的产品缺陷。

3. **[blindspot] 变更执行期间的天级扫描会产出混合状态数据** — spec L91"天级巡检：……引用扫描（全云 + K8s CRD，记录覆盖率元数据）"与执行中变更并发。扫描在两段式第一段（已上传未绑定）与第二段之间运行时，引用视图与覆盖率元数据呈现中间态，且可能触发"TLS 差异"误报路径。是否需要执行期间冻结扫描/抑制差异告警，未提及（验证窗口只保护了变更后阶段，未保护变更中阶段）。

4. **[blindspot] 回滚保护期内旧证书在云侧被外部删除** — spec L54"云侧证书库中旧证书仍存在且未过期；已删除/已过期则不自动回滚"是回滚前校验；但保护期（7~14 天）内云侧证书被他人/其他系统删除后的**主动发现**（仅靠发起回滚时才校验=被动发现）与告警策略未定义，保护期承诺与实际保护能力之间存在空窗。

5. **[blindspot] 仅指纹登记证书的"发起更换"入口一致性靠括号隐含** — UF-1 L59"点击'发起更换'（完整托管证书）"。仅指纹登记证书在台账中"发起更换"按钮是置灰、隐藏还是点击后引导补传私钥，未定义；配合 Story 4"不可自动更换"，用户遇到置灰按钮时的出路（去哪里补传私钥——见发现 3，UI 又没有该流程）形成死链。

## 总结

**SCORE: 823/1000（目标 900，未达标，需迭代）**

文档整体质量高于常见 PRD：门控依赖显式化、覆盖率双口径、盲区声明常驻、Out of Scope 论证密度都很出色。但存在三处结构性硬伤：①部分失败路径与验证窗口的关系在图/文/故事三方矛盾；②回滚对象错位（失败项 vs 成功项）贯穿全部文档；③多处 In Scope 承诺（补传私钥、不可自动变更清单、孤儿清理可见性）未传导到 UI 与故事。外加"等 CRD"开放枚举侵蚀 ≥95% 指标的可验收性。以上均为可修复项，修复后具备冲击 900 的基础。
