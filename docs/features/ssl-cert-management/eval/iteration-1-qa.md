## Phase 1 — 可测试性审计（Reasoning Audit）

总体判断：三份文档主链路（导入 → 扫描 → 清单 → 执行 → 验证 → 回滚/保护期）状态机与阈值口径基本对齐，大部分 AC 可客观验证。但审计发现 **3 处跨文档冲突** 与 **2 处关键场景缺口**，均会在测试设计阶段直接产生不可判定的用例：

| # | 类型 | 冲突/缺口 | 引用 |
|---|------|-----------|------|
| C1 | 角色-职责冲突 | 探测豁免清单维护者：spec 用户表写运维工程师，Story 5 与 UF-5 限定运维主管/审计 | spec L30「运维工程师…处理告警、维护探测豁免清单」vs Story 5「运维主管将其加入探测豁免清单」/ UF-5「仅运维主管/审计可见」 |
| C2 | 流程-UI 冲突 | 验证窗口内发现失败项可否回滚：spec 主流程步骤 8 明确可一键回滚；UF-4 仅在「执行中」状态提供回滚入口，「验证中」状态无回滚操作；Mermaid 图同样缺失该分支 | spec L83「窗口内发现失败项：可一键回滚」vs UF-4「执行中｜逐项进度 + 失败项可回滚」「验证中｜窗口倒计时 + 逐项验证状态」 |

## Phase 2 — 分维度评分

### 1. Background & Goals（100）→ **97**

- 三要素（Reason/Target/Users）：齐全且具体。Reason 用「年均数百次高危手工变更」量化痛点；Users 表三角色带职责与操作。30/30。
- 目标量化：≥90%（登记覆盖率）、≥95%（批量执行成功率）、30/14/7 天分级、100%（回滚成功率/审计留存），全部数值化。30/30。
- 逻辑一致性：目标直接对应痛点（台账化→消除手工→前置风险→变更安全）。扣 3 分：「批量执行成功率 ≥ 95%」未定义统计口径（按变更单？按月滚动？按项？），验收时无法判定达标窗口；「回滚成功率 100%（限通过目标有效性校验的项）」限定词使指标接近同义反复，但已在括号内自我声明，不另扣。37/40。

### 2. Flow Diagrams（150）→ **140**

- Mermaid 存在：flowchart TD 完整。50/50。
- 主路径完整（起→终）：A（导入）→ … → Y（结束），含拦截回流（K→A、G→H→E）。50/50。
- 判定点与异常分支：7 个判定菱形 + 拦截/阻断/部分失败/转人工/回滚失败等异常分支，覆盖优秀。但文本主流程步骤 8「窗口内发现失败项：可一键回滚」在图中无对应分支——V（验证窗口）只通向 W{全部达标或窗口关闭?}，验证期失败→回滚路径缺失。扣 10。40/50。

### 3. Functional Specs（evaluates prd-ui-functions.md，200）→ **126**

- Placement & Interaction 完整性：5 个 UF 均有 Mode/Target Page/Position；二级页面有 Entry Point 与 Return Target；导航规则明确。68/70。
- Data Requirements & States 清晰度：字段表来源/触发齐全，但 UI 状态表不一致——UF-1 有 loading/error 四态，UF-2 仅有 populated/未发现引用/扫描超期（无 loading/error），UF-3 有 empty 无 loading/error，UF-4、UF-5 只有领域状态无 loading/error。扣 10。60/70。
- Validation Rules 可执行性：UF-1 导入四类校验、UF-4 前置校验+分批 ≤50%+角色限制、UF-5 阈值范围约束（含「保护期 ≥ 验证窗口」耦合约束）均可直接转化为测试规则。58/60。
- 跨文档不一致扣分：
  - C2（-30）：spec 承诺「窗口内发现失败项：可一键回滚」，UF-4 交互流第 5 步与「验证中」状态均未提供该入口，实现者与测试者无法判断验证期是否可回滚。
  - C3（-30）：「只读查看者仅可见"到期看板"一级入口」与「台账对只读者隐藏操作按钮」同条并存，/certs 对只读角色到底可否路由进入未判定，权限用例无法编写。

  - Story 5「不可篡改地留存审计记录」——「不可篡改」无验收手段（哈希？只追加存储？），主观不可验。扣 4。

### 5. Scenario Completeness（150）→ **106**

- 端到端覆盖：换证全生命周期、bootstrap、定时巡检、配置均有触发→终态描述。扣 8：G1——华为云/AWS/Azure 引用点按指纹会被聚入变更清单，但首期无部署器，其清单行为（排除？标记？阻断？）无任何场景描述；「看得到却换不了」只解释了监控侧，未覆盖变更清单侧。52/60。
- 隐式假设显式化：K8s 凭证门控、告警渠道门控、覆盖边界声明、阈值可配范围均已显式。扣 6：导入 SAN 校验基准（G2）与「复用已有云账号凭证」的账号范围（哪些云账号纳入扫描）未显式。34/40。
- 业务规则一致性：C1 冲突——spec 用户表「运维工程师…维护探测豁免清单」与 Story 5/UF-5「仅运维主管/审计」矛盾，豁免清单的写权限用例两套文档给出相反预期。50 基准 -30 = 20/50。

### 6. Edge Case Coverage（100）→ **91**

- 错误路径：导入四类拦截、扫描超期阻断、SAN 预检拦截、回滚目标无效转人工、回滚失败告警、两段式第二段失败补偿清理孤儿证书、GitOps 管理权探测标记不可变更、reconcile 回写复检、渠道未确认提示。异常路径密度高。38/40（扣 2：云 API「限流退避」仅出现在性能注记，用户可见行为（进度停滞/重试提示）未描述）。
- 边界条件：分批 ≤50%、清单目标数上限可配、千级引用点 30 秒、容量量级（证书百张/引用点数千）、UF-5 阈值上下界及「保护期 ≥ 验证窗口」耦合约束。扣 5：同一旧证书并发发起两个变更单无互斥/锁定语义；证书/私钥上传文件大小上限未设；豁免清单并发编辑未提。30/35。
- 失败恢复：回滚语义（目标有效性校验）、转人工决策并记录、补偿清理、验证窗口结束恢复常规告警。23/25（扣 2：验证窗口关闭时仍未达标的项，转常规差异告警是隐含推断而非明文）。

### 7. Scope Clarity（100）→ **98**

- In Scope 具体交付物：14 项均为具体功能/机制（映射表、两段式、状态机、通道抽象），非模糊区域。35/35。
- Out of Scope 显式：5 项延迟项均具名并附理由与二期触发条件（「二期排期与引用点增长绑定」）。30/30。
- 与 FS/Story 一致：大体一致；扣 2：Story 4「补传私钥并升级为完整托管」在 spec In Scope 中无对应条目（In Scope 仅写 bootstrap「私钥定向回收」）。33/35。

## Phase 3 — 盲区猎捕（[blindspot]，均在 rubric 维度之外）

1. **[blindspot] 非可部署云的清单项行为未定义（G1）** — In Scope「按证书指纹（非域名）匹配同一旧证书全部引用点生成变更清单」与 Out of Scope「华为云、AWS、Azure 的证书更换部署器（二期…）」组合后：同一张旧证书若同时被阿里云 CDN 与 AWS LB 引用，清单中 AWS 项的「计划动作」是什么？若标记跳过，「全部成功」与 ≥95% 成功率的分母是否含这些项？测试设计无法构造预期结果。必须在 PRD 明确：排除/单列/阻断三选一及其对指标分母的影响。
2. **[blindspot] 导入环节 SAN 校验不可执行（G2）** — spec「SAN 覆盖（基准 = 引用资源所服务的域名集合）」对存量证书成立，但 Story 1 的新购证书导入（尚无任何引用）中「SAN 覆盖预期域名」的「预期域名」是操作者输入、还是省略该校验？当前描述是一个下游无法执行的校验步骤。
3. **[blindspot] 同一旧证书并发变更单无互斥语义** — 状态机「`草稿 → 待确认 → 执行中 → …`」未声明同一旧证书是否同时只允许一张活跃变更单。两名工程师先后（或同时）对同一指纹发起更换，第二张清单基于的扫描/旧证书状态可能已被第一张改变，部分回滚后清单「原证书 ID」失真。无任何 AC 覆盖。

### 修订指令（给 reviser）

1. 统一探测豁免清单维护角色（C1），三处文档改为同一角色。
2. UF-4 补「验证中/部分完成」状态的回滚入口与交互流步骤，Mermaid 图补「验证窗口失败 → 回滚」分支（C2）。
3. 明确只读查看者对 /certs 台账的路由可见性，消除「证书状态」歧义（C3）。
4. 定义华为云/AWS/Azure 引用点在变更清单中的处理方式及其对成功率指标分母的影响（G1/blindspot 1）。
5. 定义新购证书导入时 SAN 校验的基准来源或显式豁免该场景（G2/blindspot 2）。
6. 补同一旧证书并发变更单的互斥规则（blindspot 3）。
7. Story 1/3/5 按「AC 可验证性」扣分点补正向终态 AC、定义审计「不可篡改」验收手段。
